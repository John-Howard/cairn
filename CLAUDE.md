## Core architecture (read before building)

The product is a **single-tenant, configurable** tool: each organisation runs its own instance. Reusability comes from one configurable codebase, not multi-tenancy — so there is no cross-tenant isolation to build. Four cleanly-separated layers:

1. **Universal core** — organisation-agnostic entity model, junctions, lawful-basis machinery, external-data/lineage pattern, retention/security split.
2. **Organisation Profile** (set at setup) — legal-entity topology, applicable regimes, active modules, default-basis behaviour.
3. **Sector pack** (seed bundle) — business functions, vocabularies, rule defaults. **FRS (Fire & Rescue Service) is the first and only v1 pack.**
4. **Profile-conditioned rules** — each validation rule carries an applicability condition keyed to the profile (e.g. public-authority guards switch off for private-sector profiles).

**Build the configuration seams now, populate exactly one pack (FRS) first.** Do not build an abstract platform with no user.

### Load-bearing design decisions

These shape the schema and are easy to get subtly wrong:

- **`regime` is the first router**, above `controller_or_processor`. `general` (UK GDPR / DPA 2018 Part 2, the default) vs `law_enforcement` (Part 3, s61/s62/Sch 8/s42-APD). The Part 3 module is always built but stays dormant unless the org's **Regime Policy** activates it.
- **Dual mapping, one active.** Enforcement-domain activities can hold *both* a Part 2 basis record and a Part 3 basis record; `regime` flags which is authoritative. Switching regime must never delete the inactive mapping (reversible), and every regime change is an audited event.
- **`record_status` (draft/in_review/active/retired) vs `lifecycle_stage` (trial/live/retired) are distinct** — the record's authoring/approval state vs the processing's maturity. Do not collapse them.
- **Relational, not flat.** Article 30 is not met by a spreadsheet row per activity. Granularity lives in junction entities (`activity_datacategory` can be scoped to a specific data-subject category — essential where adults/vulnerable adults/children diverge within one activity like Home Fire Safety Visits).
- **Security is inherited from the linked System/Asset; retention is set on the activity/data-category** (with a system-suggested default the author can override). They deliberately live at different levels — see Plan §3.9.
- **Risk modelling is its own `analytics_modelling` activity**, linked via `activity_feeds` to the operational activities it serves. Automated modelling that materially affects individuals sets `lineage_granularity = record` for Art 15/22 provenance.
- **Exports are a separate mapping layer, not a storage shape.** The internal model stays clean/normalised; Art 30(1) / Art 30(2) / s61 views are generated by configurable mappings (Spec §10). Never shape stored data to an ICO template.

### Entity map

- **Config**: Organisation Profile, Regime Policy, User & Role (Spec §2).
- **Core**: Processing Activity (Spec §3) — the central record.
- **Reference/lookup vocabularies** (Spec §4, seed values §7): Legal Entity, Business Function, Data Subject / Personal Data Category, Recipient, Lawful Bases (Art 6 & s35), Special Category / Schedule 1 / Schedule 8 conditions, Security Measure, Information Asset (the IAR — formerly System/Asset, no longer a plain vocabulary), Transfer Mechanism, Retention Rule, External Data Source.
- **Junctions** (Spec §5): carry the required granularity — `activity_datasubject`, `activity_datacategory`, `activity_recipient`, `activity_security`, `activity_system`, `activity_contract`, `activity_privacynotice`, `activity_datasource`, `activity_retention`, `activity_feeds`.
- **Supporting records** (Spec §6): Lawful Basis Record, Consent, LIA/RLI, Appropriate Policy Document, Transfer, DPIA, Contract/DSA, Privacy Notice, Breach *(module)*, Complaints *(module — statutory for controllers)*, Decision-support/ADM.

Every entity implicitly carries `id`, `created_at/updated_at`, `created_by/updated_by`, `version` (prior versions retained), `change_note` (Spec §1.2) — not relisted per table.

### Validation rules

17 rules in Plan §4, expressed against concrete fields in **Spec §8**. Rules tagged `[profile]` are not universal (e.g. rule 4, the public-authority guard, only applies to a `public_authority` profile). Worked examples exercising the rules are in Spec §9 (HFSV risk model → operational targeting → processor → law-enforcement activity). In the engine (`src/cairn/rules.py`) spec rules 1–14 map 1:1 to ids "1"–"14"; spec rules 15–17 are enforced structurally (security inheritance, dashboard review surfacing, versioning/audit) rather than as engine rules; ids "18"–"21" are Cairn governance rules beyond the spec (unapproved-reference block, ADM Art 22A–22D, children's higher-protection WARN, further-processing WARN); ids "22"–"23" are IAR coupling WARNs (personal-data asset with no linked activity — asset-scoped via `evaluate_asset`; activity with data categories but no linked asset); id "24" is the asset-side rule-18 analogue, a BLOCK enforced on asset approval when the asset's supplier or a linked security measure is not approved — the asset CSV import evaluates the same rule per row and creates rows referencing unapproved reference data as `proposed` rather than approved.

## Conventions

- The overall delivery roadmap is the project plan's phases 0–6. Application build order lives in Phase 2, sub-phases 2a–2f (Project Plan §5), which track Plan §6 (2a–2e ≈ Plan stages 1a–1e; 2f ≈ Plan stage 2, DUAA alignment). Sub-phase 2a builds the core + routers + config seams and populates the FRS pack.
- Legal accuracy matters: the vocabularies (Schedule 1/8 conditions, lawful bases) are seeded from specific legislation. Verify against the latest *revised* legislation for DUAA amendments before seeding (Spec §11).
- Terminology watch-item: "ICO" is being reconstituted as the "Information Commission" under DUAA Part 6 — export labels will eventually change.
